# DPI-диагностика на iPhone: описание проекта

Дата: 2026-11-02

## Зачем

Интернет на телефоне периодически работает странно: то ли белые списки, то ли
DPI, то ли просто плохой канал. Нужна кнопка на iPhone, которая за минуту
отвечает на вопрос «что сейчас со связью» понятным вердиктом, и при этом
складывает полный лог прогона в iCloud Drive. Логи копятся, их потом
анализирует Claude (сравнивает прогоны между собой, ищет закономерности).

Движок диагностики не пишем, берём готовый
[dpi-detector](https://github.com/Runnin4ik/dpi-detector) (Python, MIT,
v4.2.4). Он уже умеет всё нужное: DNS, доступность доменов с классификацией
ошибок, обрыв TCP 16–20 КБ (сигнатура белого списка), Telegram. Проект
это обёртка над ним под iPhone.

## Цели

1. Запуск одним нажатием с домашнего экрана или виджета, без открытия
   терминала и без ввода команд.
2. Короткий отчёт на экране: вердикт в одну-две фразы плюс три-пять строк
   фактов, на которых он основан.
3. Полный лог каждого прогона в iCloud Drive, с датой, режимом и именем сети
   в имени файла.
4. Два режима: быстрый (около минуты, без тяжёлого трафика) и полный
   (всё, включая Telegram и перебор SNI).
5. Строка сравнения с прошлым прогоном на той же сети.

## Не цели

- Отдельное нативное приложение, App Store, аккаунт разработчика.
- Фоновый мониторинг, уведомления, графики.
- Изменения в самом dpi-detector. Он используется как есть, обновляется
  осознанно, по решению владельца.
- Обход блокировок. Только диагностика.

## Анти-цели (что сделает проект провалом)

- **Ложная тревога.** Вердикт «белый список» или «подмена DNS» на плохом
  сигнале в метро. Владелец явно выбрал: лучше сказать «всё в порядке» и
  ошибиться, чем напугать. Правила вердикта строгие, при сомнении вердикт
  нейтральный, а подозрения уходят в строки фактов.
- **Сломанный парсер после обновления движка.** Версия dpi-detector
  закреплена, обновление это отдельный шаг с прогоном тестов парсера.
- **Трата мобильного трафика без спроса.** Быстрый режим не качает
  мегабайты; полный режим явно называется полным.

## Ограничения

- iOS, терминал **a-Shell mini** (установлен). Только чистый Python,
  пакетов с нативными расширениями нет. dpi-detector тянет httpx, rich,
  PyYAML, все чистые, по README автора в a-Shell работает.
- В a-Shell нет `fork`, поэтому `subprocess` из Python не работает.
  Обёртка не запускает движок как дочерний процесс; шаги идут
  последовательными командами shell, которые исполняет Команда (Shortcuts).
- a-Shell из Shortcuts выполняет команды либо «в расширении» (лёгкий режим,
  без долгих сетевых задач), либо «в приложении». Нам нужен режим «в
  приложении», с возвратом в Shortcuts через `open shortcuts://`.
- a-Shell не видит iCloud Drive напрямую. Его `~/Documents` это «На iPhone /
  a-Shell». В iCloud файлы кладёт сама Команда действием «Сохранить файл».
- Интерактивное меню dpi-detector в a-Shell не работает, только `--batch`
  с явным `-t`.
- Прогон идёт на той сети, на которой сейчас телефон. VPN и обходчики на
  время прогона должны быть выключены, иначе результат бессмысленный.
  Тест 0 движка на iOS VPN **не увидит**: имя адаптера он определяет только
  на Windows, а поиск процессов-обходчиков через `ps` в a-Shell молча
  падает и печатает «не обнаружен». Поэтому признаки VPN/прокси ищет сама
  обёртка (см. правило 0б).

## Что решено

### Состав

Три части:

1. **dpi-detector** (чужой код), клонируется в a-Shell, закреплён на
   конкретном коммите.
2. **Обёртка** (наш код, Python, в этой папке): запускает движок в нужном
   режиме, разбирает его текстовый лог, строит структурированный JSON,
   считает вердикт, печатает короткий отчёт, сравнивает с прошлым прогоном.
3. **Три Команды (Shortcuts)** на телефоне: «Сеть: быстро», «Сеть:
   полностью» и «Сеть: белые SNI». Каждая собирает имя сети, запускает
   обёртку в a-Shell в своём режиме, показывает короткий отчёт и сохраняет
   файлы в iCloud Drive. Первые две для ежедневного пользования, третья
   на случай, когда захочется настроить обход.

### Как это течёт

```
Команда
  ├─ «Получить сведения о сети» → SSID Wi-Fi или имя оператора
  ├─ a-Shell «Выполнить команду» (в приложении):
  │     cd ~/Documents/dpiphone
  │     python run.py --mode quick --net "<имя сети>"
  │     open shortcuts://
  ├─ a-Shell «Получить файл» out/summary.txt → «Показать результат»
  ├─ a-Shell «Получить файл» out/<имя>.log  → «Сохранить файл» в iCloud Drive/DPI Logs
  └─ a-Shell «Получить файл» out/<имя>.json → «Сохранить файл» в iCloud Drive/DPI Logs
```

`run.py` внутри a-Shell не может вызвать `python dpi_detector.py` как
подпроцесс. Поэтому обёртка состоит из двух команд, которые Команда
выполняет подряд в одном действии «Выполнить команду»:

```
python ../dpi-detector/dpi_detector.py -t 0123 --batch -c 20 -o out/raw.log > out/console.log 2>&1
python report.py --mode quick --net "<имя сети>"
```

Первая пишет сырой лог движка двумя путями: `-o` сохраняет весь текст
консоли без разметки, но только в самом конце прогона, а перенаправление
stdout пишет по ходу. Если движок упал на полпути или iOS усыпила
a-Shell, `raw.log` не появится, а `console.log` останется с тем, что
успело выйти. `report.py` берёт `raw.log`, если он есть, иначе
`console.log`; в последнем случае вердикт всегда «не удалось», а лог всё
равно уходит в iCloud с пометкой «неполный». Парсер не завязан на ширину
терминала и кадры прогресс-баров: у двух путей они отличаются.

Решение разбирать текстовый лог, а не импортировать внутренности движка:
лог это и есть то, что потом читает Claude, его формат и словарь статусов
(«Легенда» в движке: OK, TLS RST, TLS DROP, DETECTED, ...) стабильнее
имён функций в активно меняющемся проекте. Цена: парсер завязан на
формат вывода конкретной версии, поэтому версия закреплена.

### Режимы

| Режим   | Тесты движка           | Что проверяет                                    | Время, трафик |
|---------|------------------------|--------------------------------------------------|---------------|
| quick   | 0, 1, 2, 3             | сеть и ASN, DNS, домены, обрыв 16–20 КБ          | ~1–2 мин, мало |
| full    | 0, 1, 2, 3, 5          | то же плюс Telegram (30 МБ + 10 МБ)              | ~3–5 мин, десятки МБ |
| sni     | 3, 4                   | обрыв 16–20 КБ и перебор белых SNI для обрывающихся провайдеров | при белом списке 10+ мин, десятки МБ |

Тест 4 (перебор белых SNI) из полного режима убран по решению владельца:
это инструмент обхода, а не диагноза, и при реальном белом списке он
перебирает до 188 имён на каждого обрывающегося провайдера. Он вынесен
в отдельный режим `sni` и отдельную, третью Команду «Сеть: белые SNI».
Его результат (найденные SNI по провайдерам) идёт в JSON и в полный лог,
в короткий отчёт попадает одной строкой: «Белые SNI: найдены для 5 из 7
провайдеров» или «не найдены». В правилах вердикта режим `sni` не
участвует: вердикт в нём всегда только по правилу 2 (белый список) или
«всё в порядке», базой для сравнения он не становится.

Параллельность `-c 20` вместо 50 по умолчанию: на телефоне и мобильной сети
50 даёт ложные таймауты пула сокетов. Это моё решение, порог можно
подвинуть по результатам.

### Файлы

Папка в iCloud Drive: `DPI Logs/`. Имя файла:
`2026-11-02_14-32_quick_MTS.log` и такой же `.json`. Имя сети очищается
от пробелов и символов, непригодных для имени файла; если сеть не
определилась, пишется `unknown`.

- `.log` — сырой вывод движка как есть, плюс шапка от обёртки (дата, режим,
  сеть, версия движка, версия обёртки).
- `.json` — структурированный результат: по каждому тесту счётчики и списки
  (какие домены с каким статусом, какие хостинги DETECTED), вердикт, строки
  фактов, ссылка на предыдущий прогон и его отличия.

Внутри a-Shell обёртка держит `out/last.json` для сравнения со следующим
прогоном, и папку `history/` с JSON всех прогонов (они маленькие). Полные
логи в a-Shell не копятся, их место в iCloud.

### Короткий отчёт

Текст, который показывает Команда. Структура фиксированная:

```
Похоже, включён белый список: Hetzner, Cloudflare, AWS обрываются
после 16 КБ, Gcore и Яндекс в норме.

Сеть: MTS · AS8359 MTS PJSC · 83.149.x.x
DNS: 38/40 UDP, 33/35 DoH · подмены нет
Сайты: 27/35 OK · TLS RST 6 · DROP 2
Хостинги 16–20 КБ: 31/70 OK · обрыв: Hetzner, Cloudflare, AWS, CDN77
Прошлый прогон на MTS (вчера 19:40): тогда обрывов не было
```

Первая строка вердикт, затем пустая, затем факты. В полном режиме
добавляется строка Telegram. Если тест не удалось выполнить, его строка
так и говорит: «DNS: не выполнен».

### Корзины статусов движка

Правила вердикта оперируют не отдельными статусами, а тремя корзинами.
Реальный словарь движка (`utils/error_classifier.py`, легенда в
`cli/ui.py`) раскладывается так:

| Корзина | Статусы движка |
|---------|----------------|
| **блокировка** (кто-то активно вмешался) | TLS RST, TCP RST, TLS ALERT, TLS BLOCK, TLS SPOOF, TLS EOF, TLS MITM, TLS ABORT, TCP ABORT, BLOCKED (HTTP 451), ISP PAGE, DNS FAKE, красный REDIR (на чужой домен); в тесте 3 — DETECTED |
| **канал** (пакеты пропали, никто не ответил) | TLS DROP, SYN DROP, TIMEOUT, READ TIMEOUT, SEND TIMEOUT, POOL TIMEOUT, NET UNREACH, HOST UNREACH |
| **шум** (не говорит ни о чём) | OK, зелёный REDIR, NO TLS1.3, NO CA BUNDLE, DNS FAIL, REFUSED, LOCAL IP, UNKNOWN, OS ERR, ERR |

TLS DROP и SYN DROP сознательно отнесены к каналу, а не к блокировке:
молчаливый дроп пакетов неотличим от плохого сигнала в метро, а владелец
просил при сомнении говорить «всё в порядке». Это моё решение. Цена:
оператор, который блокирует именно молчаливым дропом, будет выглядеть
как плохой канал; в строке фактов дропы всё равно показываются числом.

Статуса TLS DPI в движке нет (только в легенде), парсер его не ждёт.
Статуса «смешанный» по провайдеру в тесте 3 движок тоже не выдаёт;
«провайдер обрывается» для правил ниже означает: все его цели DETECTED.

### Вердикт: правила

Правила проверяются по порядку, первое сработавшее даёт вердикт. Смешанные
картины допускаются только там, где это явно указано.

0а. **Нет данных.** Движок не дошёл до конца, или тест 0 не получил
   внешний IP, или в тестах 2–3 больше половины результатов из корзины
   «канал» и ни одного из корзины «блокировка». Вердикт: «Сеть почти не
   отвечает, проверить не удалось». Это не вердикт о блокировке.

0б. **Прогон под VPN или прокси.** В DNS-ответах есть FakeIP
   (198.18.0.0/15, сигнатура локального прокси в fake-ip режиме; движок
   сам пишет «отключите прокси/FakeIP»), или ASN внешнего IP из теста 0
   не совпадает с ASN последнего полноценного прогона на сети с тем же
   именем. Вердикт: «Похоже, включён VPN или прокси, прогон не о вашем
   операторе». FakeIP из правила 1 убран: это не подмена оператором.

1. **Подмена DNS появилась.** Движок сообщил «Подмена резолвера» (перехват
   по брендам) или «Подмена ответов» хотя бы у двух UDP-резолверов, **и**
   в базовом прогоне на этой сети подмены не было. Вердикт: «Оператор
   начал подменять DNS». Если одновременно сработало правило 2, вердикт
   «Смешанная картина: подмена DNS и белый список».

   Если подмена есть и была в базе, или базы нет, это **норма сети**, а не
   событие: в вердикт она не попадает, в фактах стоит строка «DNS:
   подмена ответов у 30/37 UDP (перехват порта 53)». Причина: у
   оператора, который прозрачно перехватывает порт 53, это будет каждый
   прогон, и постоянный вердикт «подмена DNS» заслонил бы белый список,
   ради которого всё затевалось.

2. **Белый список.** В тесте 3 DETECTED не меньше чем у половины целей, и
   они покрывают не меньше трёх разных провайдеров, которые обрываются
   целиком (все цели провайдера DETECTED). Вердикт: «Похоже, включён
   белый список», с перечнем обрывающихся и нормальных провайдеров.

3. **Новые блокировки.** Есть база на этой же сети, и число доменов из
   корзины «блокировка» выросло минимум на три по сравнению с базой.
   Вердикт: «Появились новые блокировки: <домены>». Без базы правило не
   срабатывает: в списке движка заведомо много доменов, которые в России
   заблокированы всегда, их «красный» статус норма, а не событие.

4. **Плохой канал.** Корзина «блокировка» не выросла относительно базы
   (или базы нет), но корзина «канал» покрывает четверть и более целей
   тестов 2–3, либо в полном режиме Telegram показал замедление или
   обрыв. Вердикт: «Блокировок не вижу, похоже на качество канала».

5. **Всё в порядке.** Вердикт: «Всё в порядке», и ниже факты. Если есть
   заблокированные домены, в фактах так и будет: «заблокировано как
   обычно: 8».

Пороги (половина, три провайдера, плюс три домена, четверть)
это мои начальные значения. Они живут в одном месте в коде и подбираются
по реальным логам. Направление подбора задано: при сомнении в сторону
«всё в порядке».

### Сравнение с прошлым прогоном

**База** это последний *полноценный* прогон с тем же именем сети (любого
режима): движок дошёл до конца, вердикт не 0а и не 0б. Прогоны «нет
данных» и «под VPN» в историю пишутся, но базой не становятся. Иначе
один прогон в метро или под VPN сделал бы следующий нормальный прогон
«появились новые блокировки».

Сравниваются: подмена DNS (да/нет), множество доменов из корзины
«блокировка», множество провайдеров, обрывающихся целиком в тесте 3.
Строка отчёта: «без изменений» либо перечисление «появилось: ... /
исчезло: ...». Если базы на этой сети нет, строка: «первый прогон на
этой сети».

### Установка на телефон

Один раз, в a-Shell:

```
lg2 clone <репозиторий обёртки> ~/Documents/dpiphone
cd ~/Documents/dpiphone
sh install.sh
```

`install.sh` клонирует dpi-detector в соседнюю папку, переключает его на
закреплённый коммит, ставит зависимости через pip. Команды (Shortcuts)
импортируются по ссылке iCloud или собираются вручную по инструкции в
README проекта (действий в них меньше десяти).

Обёртка живёт в приватном репозитории на GitHub владельца; это мой выбор
ради `lg2 clone` и простого обновления, можно заменить копированием через
Файлы.

### Разработка и проверка на Mac

Обёртка это обычный Python 3.8+, на Mac запускается так же. Движок на Mac
тоже работает, так что первый реальный прогон делается на Mac, его сырой
лог становится фикстурой для тестов парсера. Тесты парсера и правил
вердикта гоняются на Mac на фикстурах. На телефоне проверяется только
то, что нельзя проверить на Mac: сам a-Shell, Команда, iCloud.

Три риска, которые надо снять первыми, до остального кода, пробным
запуском на телефоне:

1. dpi-detector v4.2.4 с `-t 0123 --batch -o` реально работает в a-Shell
   mini на этом телефоне и на мобильной сети.
2. Команда с a-Shell «Выполнить команду» в режиме «в приложении»
   возвращается в Shortcuts и продолжает следующие действия.
3. «Получить файл» из a-Shell и «Сохранить файл» в iCloud Drive без
   диалога работают в одной Команде.

## Что остаётся строителю

- Точный разбор текстового лога движка: регулярные выражения, обработка
  обрезанных строк, прогресс-баров, многострочных таблиц.
- Точный текст вердиктов и строк фактов в пределах заданной структуры.
- Формат JSON.
- Сборка Команд: действия, параметры, порядок. Если «Получить файл»
  окажется неудобным, допустимо собрать файлы в один `.zip` в обёртке.
- Обработка ситуации «сеть не определилась» и «движок упал на полпути»
  (лог сохраняется всё равно, вердикт «не удалось»).
- Поведение при повторном запуске, пока прошлый ещё идёт (достаточно
  не падать).
